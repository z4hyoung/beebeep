## 2. 模块设计

### 2.1 传输层抽象（M2 核心，`src/core/StreamDevice.*` 新增）

依据 core 报告 §B/§C：`ConnectionSocket` 只有 2 个建连入口依赖 QTcpSocket，其余公有 API 全部流无关。

- **`StreamDevice : QObject`** 接口：`connectToHost/connectToService/setSocketDescriptor/adoptSocket/abort/close/flush/ioDevice/peerAddress/peerPort/errorString/isConnectingState` + 信号 `connected/readyRead/bytesWritten/errorOccurred(QAbstractSocket::SocketError)/disconnected`
- **`ConnectionSocket` 改为组合** `StreamDevice* mp_stream`；`readBlock` 的 `QDataStream(this)` → `QDataStream(mp_stream->ioDevice())`（core/ConnectionSocket.cpp:155）；构造里的 socketOption/setProxy 移入 Tcp 实现
- **信号契约（不可破坏）**：必须继续发出 `error(QAbstractSocket::SocketError)` 和 `disconnected()`（core/CoreConnection.cpp:158-159 按签名 connect）；BT 侧把 `QBluetoothSocket::errorOccurred` 映射到 `QAbstractSocket::SocketError` 枚举
- **分两步走**：第一步纯"继承→组合"，TCP 行为逐字节不变（`serializeData/readBlock` 不动一行）；第二步接入 BT 适配器
- **握手适配**：BT 客户端在 `QBluetoothSocket::connected` 后发同样的 `connected()` 信号触发 HELLO；**BT 服务端不主动发 HELLO**（照抄 TCP 服务端的不对称逻辑，core/ConnectionSocket.cpp:505）；连接超时 16-tick 对 BT 放宽（SDP 发现可能慢）

### 2.2 蓝牙模块（`src/bluetooth/` 新增）

| 类 | 职责 |
|---|---|
| `BtManager` | 总控：本机适配器状态、`QBluetoothPermission` 权限申请（Qt 6.5+，macOS 必需）、启动/停止发现与监听 |
| `BtDiscoverer` | `QBluetoothDeviceDiscoveryAgent`(ClassicMethod) + SDP 服务 UUID 过滤 → `btPeerFound(QBluetoothAddress)` 信号（**不伪装成 QHostAddress**，方案 1，见 core 报告 §D.2——NetworkManager 的 IP 白名单会拦截合成地址） |
| `BtListener` | `QBluetoothServer`(RfcommProtocol) 监听 + SDP 注册自定义 UUID → `newConnection(QBluetoothSocket*)` |
| `StreamDeviceBt` | `QBluetoothSocket` 适配进 StreamDevice（含信号映射、合成 peerAddress——以 **BT MAC 为键**映射进 IPv6 link-local fe80::/64 空间，会话期稳定，满足 hasConnection 去重） |

- Core 注入点：`Core::btPeerFound`（镜像 `newPeerFound` 的防重检查链，core/CoreConnection.cpp:91-126 逐条移植：自连→比对本机 BT 地址）；服务端 `Core::checkNewBtConnection(socket*)`（等价 core/CoreConnection.cpp:135-150）
- 服务 UUID：`Config.h` 固定常量（实现时 `uuidgen` 生成）
- 设置项（Settings 双写 rc+ini，参照 core 报告 §F.2 位置）：`UseBluetooth`、`BluetoothAutoReconnect`、`BluetoothDeviceName`

### 2.3 内联文件传输（`Message::FileChunk`，蓝牙路径）

依据 core 报告 §E 的完整设计，关键点：

- **协议扩展**（全部尾部追加，前向兼容——旧版对未知消息头丢弃但保持连接，core/Connection.cpp:63-69）：
  - `Message::Type` 枚举尾加 `FileChunk`（头串 `"BEE-FCHU"`，Protocol.cpp 两处 switch）
  - `Message` 标志尾加 `InlineFile`（表示"内联传输，勿连 6476"）
  - 块格式：`fileId | chunkIndex | totalChunks | byteOffset | chunkSize`（U+2029 分隔）+ **块数据 base64**（⚠️ 最关键决策：协议是 QString 文本框架，裸二进制会被 `toMessage` 的 split 切碎，core/Protocol.cpp:146；base64 后 64KiB 块膨胀 ~33%，在 RFCOMM 100-250KB/s 下可接受）
  - 块大小 64KiB（天然 16 字节对齐，满足 Rijndael 加密约束）
- **流控**：停等（接收方每块回 ACK 再发下一块）——复刻现有 6476 通道的停等模式；窗口=4 滑窗作为性能优化项后置
- **挂载点**：`InlineFileTransferPeer` **挂进 `FileTransfer` 类内部统一 peer 列表**（core 报告推荐方案）——GUI 的进度条/暂停/取消完全无感零改动
- **压缩**：内联文件应用层不压缩（qCompress 是每消息整体压缩，块级压缩破坏 hash 校验粒度）；连接级压缩协商不受影响
- **降级**：>5MB 或对端为老版本（protocolVersion 检查）→ 回退 6476 老路径（LAN 场景继续用）

### 2.4 UI 重构（微信式）

依据 gui 报告：现状是"Tab 主窗口 + 浮动聊天窗"，消息是 QTextBrowser 流式 HTML。

- **主窗口**：新建 `GuiMainWindow`（QSplitter：左 260px 会话列表 + 右 GuiChat 嵌入区）。GuiChat 本身是 QWidget 可直接嵌入（gui 报告 §A）；浮窗逻辑（`createFloatingChat`）旁路保留但默认不触发
- **会话列表**：QListView + 自绘 delegate（头像/名称/最后消息摘要/相对时间/未读角标）；数据从 ChatManager 取最后一条消息；传输中显示小进度环
- **气泡渲染**：落点 `GuiChatMessage::formatMessage/formatSystemMessage`（GuiChatMessage.cpp:72/167）+ `insertHtml`（GuiChat.cpp:741）。方案：HTML 表格/背景色块（自己右侧强调色、对方左侧白、系统消息居中灰字）。⚠️ QTextDocument 富文本**不支持 border-radius**——第一版用直角色块（QQ 早期风格，微信气泡圆角很小观感接近），圆角气泡列为 COULD（需换自绘消息列表，成本高）
- **输入区**：复用 `GuiMessageEdit`（回车发送已有）+ 新工具行 [emoji][📎][发送]
- **砍除**：编译级（voicechat✅已禁/hunspell✅已禁/sharedesktop/plugins 游戏）+ UI 级（群组/ShareBox/Hive/Buzz/截图入口/复杂设置页，action 清单见 gui 报告 §E）
- **Dock 角标**：新增 `desktop/DockBadge_mac.mm`，挂 `GuiMain` 的未读更新点（gui 报告 §H）
- **中文修复**：`beebeep_cn.ts → beebeep_zh.ts`（或加映射），上游 bug：中文系统默认回退英文（Settings.cpp:1459 语言匹配 `zh` vs 文件名 `cn`）

### 2.5 品牌与共存（M0 实测教训）

- `TARGET = yongbeep`、应用显示名 "YongBEEP"、独立图标、`QCoreApplication::setApplicationName("YongBEEP")` → 单实例锁/配置目录/数据目录与官方 BeeBEEP 完全隔离（M0 冒烟实测：不改名会被官方运行实例的单实例锁拦截）
- 收益：开发期可与你安装的官方版并存对照

### 2.6 权限与平台接入（build 报告实证）

- `QT += bluetooth` 加在 src/src.pro:42
- macOS：**Info.plist 加 `NSBluetoothAlwaysUsageDescription`** + 代码里 `QBluetoothPermission` 申请（Qt 6.5+ 权限系统）；QtBluetooth.framework 已内链 IOBluetooth/CoreBluetooth，无需手动链接
- Windows：**原生 Win32 蓝牙后端**（`src/bluetooth/BtWinWorker.*`，2026-11 实测落地）。MinGW 构建的 Qt 不含可用的 QtBluetooth 后端（WinRT 后端仅存在于 MSVC 构建），故 Windows 端改用 `BluetoothAPIs.h` + AF_BTH 套接字直接对接系统栈：`BluetoothFindFirstDevice` 扫描 + 按设备 `WSALookupService` SDP 查询（服务发布走 `WSASetService` 简单模式，系统自动从 CSADDR_INFO 构造 ProtocolDescriptorList），全部阻塞调用收敛在 BtWinWorker 线程；传输层以 `NativeBtSocket`（QIODevice 包装）实现 StreamDevice 契约。原计划"MSVC x64 + Qt Connectivity"的纯 QtBluetooth 路径不再必需
- 最低系统：macOS 14.4+（brew Qt 6.12 的约束；Windows 10 1903+）

## 3. 关键技术决策记录（ADR 摘要）

| # | 决策 | 理由 | 放弃的选项 |
|---|---|---|---|
| D1 | 经典 RFCOMM（两端 Qt 对称） | 100-250KB/s 满足 5MB/20-50s；两端同一套代码 | BLE GATT（慢 2 倍+角色固定）；原生 API 双栈（工作量大 3 倍） |
| D2 | ConnectionSocket 继承→组合 | 仅 2 个建连入口耦合 TCP；上层零改动 | 代理继承 QBluetoothSocket（多重继承地狱）；fork 双份 Connection 类（回归面翻倍） |
| D3 | 蓝牙发现走独立信号（不伪装 IP） | NetworkManager IP 白名单会拦合成地址（core 报告 D.2 方案 2 侵入面更大） | 合成 QHostAddress 复用现有信号 |
| D4 | 文件分块 base64 进消息通道 | 协议是 QString 文本框架，裸二进制必碎（最大陷阱）；免去重写二进制协议 | 扩展 Message 二进制字段（动序列化核心，回归风险大） |
| D5 | 内联传输挂进 FileTransfer 统一列表 | GUI 进度/暂停/取消零改动 | 独立管理器（UI 要双轨） |
| D6 | TARGET 改名 yongbeep | M0 实测锁冲突；品牌化本就要做 | 共用 beebeep 名（与官方互斥） |
| D7 | 气泡用 HTML 色块（非圆角） | QTextDocument 不支持 border-radius；直角色块零风险 | 自绘消息列表（圆角完美但成本高，列 COULD） |

## 7. 风险 Top5（core 报告 G.2 全文照录执行）

1. `disconnected()` 手工补发/双发 → 连接泄漏或 double-deleteLater（测试断言：连接数守恒）
2. `QDataStream` 设备指针在 adopt/重连时更换 → 握手周期内指针必须稳定
3. 16 字节对齐 × U+2029 分隔符污染（base64 已规避，测试加断言）
4. ConnectionSocket 被 6475/6476 双复用 → 文件通道 HELLO 不对称时序不可破坏
5. BT 合成地址不稳定 → 重复连接误判；以 MAC 为键、会话期不变
