## 1. 项目背景

用户 Mac（Apple Silicon / macOS 25.6 / 已装 BeeBEEP 5.8.5）与邻近的 Windows 电脑各连接自己的 IP 网络，网络层不通，无法使用 BeeBEEP 原生的局域网通信。目标是在 BeeBEEP 开源代码（GPLv3）基础上，构建一个**只保留文本聊天 + 文件传输**的极简双端 IM：Mac 与 Windows 通过**蓝牙**直连通信，界面改为**微信/QQ 风格**。

## 2. 需求边界

### 2.1 已确认需求
| # | 需求 | 说明 |
|---|---|---|
| R1 | 蓝牙通信：文本 + 文件 | Mac ↔ Windows，物理邻近但 IP 网络隔离；文件 ≤5MB |
| R2 | UI 改为微信/QQ 式 | 左侧会话列表 + 右侧气泡聊天 + 底部输入栏 |
| R3 | 精简：只要文本和文件 | 其余功能（语音/桌面共享/游戏/群组/截图/拼写…）全部移除 |
| R4 | 代码仓库 | 用户自己 GitHub 账户下的独立仓库 |

### 2.2 明确不做（Non-Goals）
- 公网/互联网通信、NAT 穿透（官方架构即无此能力，需求为"邻近设备"）
- 与官方未修改版 BeeBEEP 的蓝牙互通（蓝牙协议为本项目私有；LAN 上仍兼容互通）
- 大文件（>5MB）优化、断点续传多会话管理

## 3. 候选方案与选型

| 方案 | 描述 | 结论 |
|---|---|---|
| 一、零代码 | 系统级蓝牙配对组 PAN 网络 + BeeBEEP 自带"按 IP 连接" | **不满足 R2/R3**（界面/功能原样），仅作为开发期临时通信通道 |
| **二、自建分支改造（推荐）** | 从官方 SVN 导出 5.9.2-dev 基线，自建仓库，加蓝牙传输层 + 重做极简 UI | 满足 R1–R4 全部需求；工作量可控（见 §6） |
| 三、等官方 6.0 | 2026-12 发布，官方自带蓝牙 Mesh + 新 UI | 功能未知是否满足 R2/R3；作为**检查点**——发布后评估，若满足则本项目止损归档 |

**选型：方案二**，方案一为辅助，方案三为检查点（详见 §7 风险 R6）。

## 4. 总体方案概述

> 此处只给结论性描述，模块/接口/协议级细节在《02-技术设计》中展开评审。

### 4.1 传输：经典蓝牙 RFCOMM（优先）+ 降级链
- 两端 Qt（macOS/IOBluetooth、Windows/WinRT）均官方支持 RFCOMM，代码两端对称
- 实测预期吞吐 100–250 KB/s：5MB 文件 20–50s，文本亚秒 → 满足 R1
- 降级链：RFCOMM（方案A）→ BLE GATT（方案B，50–110KB/s，免配对）→ 原生 API（方案C，仅当 Qt 后端在 macOS 25.6 不可用时）
- 复用 BeeBEEP 现有 ECDH + AES-256，蓝牙连接自动获得端到端加密

### 4.2 代码改动收敛在三处
1. **传输层抽象**：`ConnectionSocket` 由"继承 QTcpSocket"改为"组合 QIODevice"（TCP/蓝牙共用，上层消息模型 `Message`/`Chat` 零改动）
2. **文件走消息通道**：≤5MB 分块（64KB/块）经加密消息通道传输，复用现有进度 UI；LAN TCP 路径保留
3. **UI 重构 + 功能裁剪**：主窗口重组为微信式两栏；裁剪用"编译开关 + 隐藏入口"两级手段

### 4.3 仓库
GitHub 上无官方仓库（第三方镜像已停更且不可信），从**官方 SourceForge SVN r1609（5.9.2-dev）**导出为初始提交，推入用户自建空仓库 `YongBEEP`；`main` 保持基线纯净并打 tag。

## 5. 研发流程（阶段门机制）——本建议书的核心承诺

**从本阶段起，每个阶段产出正式文档，经你评审批准后才进入下一阶段；未经批准不写一行产品代码。**

| 阶段 | 交付物 | 评审门 | 你的角色 | 我的工作 |
|---|---|---|---|---|
| **S0 方案** | 本文档 | **G0**：批准/修改 | 审批 | 按意见修订 |
| **S1 产品设计** | 《01-产品设计》：目标用户与场景、功能清单（含砍除清单）、界面原型图、交互流程、产品验收标准 | **G1** | 审批原型与功能取舍 | 产出并修订 |
| **S2 技术设计** | 《02-技术设计》：架构图、模块划分、类/接口定义、蓝牙协议与消息格式、UI 实现方案、构建方案、代码改动清单与影响面 | **G2** | 审批技术方案 | 产出并修订 |
| **S3 编码** | feature 分支逐个交付（bt-transport → bt-file → ui-wechat → strip-features），每个 feature 附改动说明 | **G3**：代码走查 | 随时可看 diff/试用中间版 | 编码 + 自测 |
| **S4 测试** | 《03-测试方案与报告》：单元/集成/双机验收/性能与稳定性测试 | **G4**：验收 | 参与双机实测验收 | 执行并出报告 |

里程碑 M0（环境+基线编译）~M5（打包）作为 S3/S4 内部节点保留，定义不变（见调研报告附录/后续技术设计文档）。

## 7. 风险与对策

| # | 风险 | 等级 | 对策 |
|---|---|---|---|
| R1 | Qt 蓝牙后端在 macOS 25.6 兼容性未知 | 高 | M1 第一周独立 PoC 实测，不通过走 BLE/原生降级链 |
| R2 | Windows 未配对设备发现路径行为不确定 | 中 | M1 同步实测；保底方案=先系统配对 |
| R3 | 吞吐不达标（<100KB/s） | 中 | 调缓冲/块大小；再不行接受 BLE 量级（用户已确认 5MB 可接受 50–100s） |
| R4 | 5.9.2-dev 基线编译问题（Qt6/Qt5 选择） | 中 | M0 阶梯验证（brew qt6 → qt@5 → 官方安装器），SVN 可随时回退旧修订版 |
| R5 | UI 气泡与微信观感差距 | 中 | G1 阶段先用原型图对齐预期再动手 |
| R6 | 官方 6.0（2026-12）发布后重复建设 | 中 | 检查点评估：满足需求则本项目归档止损；本方案改动克制、沉没成本低 |
